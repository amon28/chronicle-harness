# Decisions

Short records of choices that shaped the app, newest areas last. Each: what, why, what it costs.

1. **Rename to Chronicle, keep OpenCode Go support.** The app is now chat + roleplay + agent, not just OpenCode. Only the name and icon (a fantasy book) changed.
2. **Secrets in the Android Keystore.** API/Exa/GitHub/Microlink keys are split out of IndexedDB. Auto-backup to Google is off (`allowBackup=false`) so chats and memories are not uploaded; the in-app backup is the way to move data.
3. **Files are replaced, never mutated** in workspaces, so checkpoints/undo are cheap shallow snapshots.
4. **Phone-folder access has three modes** (Review / Auto / Read-only), per chat. Review stages every write/delete and shows a diff sheet; Auto writes at once and logs what was there so a reply can be undone; Read-only refuses. Reason: let the user skip accept/reject without losing the safety net.
5. **Mods are sandboxed iframes with explicit permissions** (`tools`, `commands`, `chat`, `request`, `storage`, `net:<host>`, `search`). An install sheet is always required, even for mods the assistant writes. Cost: mods can't touch the app's screens.
6. **Web search is extendable by mods, not editable.** `mod.searchSource` adds sources; the built-in engines and the hidden browser tool are fixed code. Reason: a mod can add reach without being able to weaken the network safety rules.
7. **Native web reads refuse private networks at every redirect hop** (and the hidden browser blocks private hosts). Cleartext http stays allowed because the user runs `opencode serve` on their own PC.
8. **Tool output is data, not orders.** The tools prompt says so; memory learning drops memories whose distinctive words come from skills/files/pages rather than the user's own message.
9. **Memory: send fewer, relevant facts.** Per-chat memory limit with relevance + recency + pins; optional embedding (Smart memory, in a worker so the UI never freezes); past-chat notes are sent bullet by bullet. Tidy up proposes merges for review, with undo.
10. **Agent creation tools always ask.** `save_persona`, `save_character`, `save_lorebook` show an approval sheet. They update existing personas in place (built-ins included) instead of copying; lookups are by id, exact or unique partial name, and kind-aware (chat persona vs roleplay character can share a name).
11. **Replies run per chat.** Leaving a chat no longer stops its reply; the side menu shows a spinner while busy and a blue dot when it finished unseen. Only compact/impersonate/continue, which belong to the screen, stop on leaving.
12. **Custom dropdown sheet instead of Android's list.** It must never cancel `touchstart` (that also cancels the tap's click and nothing opens on a phone).
13. **Chub import is opt-in.** Only a tap on a Download/PNG control arms card capture; opening a character page imports nothing.
14. **Compact menus like Chub.** Chat ⋮ is a small popover with a "More" section; 📎 is a quick-actions popover; roleplay characters open their own page before a chat starts (assistants start immediately).
15. **Roleplay image generation is parked** by the owner as a later option.
16. **Test discipline.** Lint + unit + all e2e before every push; features are not "done" on desktop tests alone — each has a step list in `docs/DEVICE-TESTS-FULL.md`, and the short on-phone checklist `docs/DEVICE-TESTS.md` (37 steps) holds what only a phone can show.
17. **Questions belong to their chat.** The ask sheet opens only in the chat that asked (a ❓ mark in the side menu shows who is waiting), never answers on an outside tap (hide ≠ skip), and several questions are pages with back/next. Reason: background chats made questions pop up in the wrong place and a stray tap silently skipped them.
18. **The mod API is open by design, with permissions as the price.** Mods can add tools, commands, search sources (`search`), panels (`panel`) and see/block/rewrite tool calls (`toolhook`). Each new reach is its own permission shown at install, sensitive ones flagged. Mods still can't change app screens, the built-in engines, or the network safety rules.
19. **MCP over Streamable HTTP only** (external, LAN, or on-phone via Termux). stdio servers need a bridge (supergateway/mcp-proxy); the legacy SSE-only transport and OAuth sign-in are not supported. Per-tool switches keep the prompt small.
20. **Tool-turn retries.** A transient error (TLS read error, reset, 5xx) in a later step of an agent turn is retried when that step has produced nothing yet; earlier tool rounds don't block it.
21. **Backups are streamed.** Reading every chat's files into memory, zipping them and sending one giant base64 string through the bridge crashed the app on a phone with a lot of data. Now each file is read, zipped (images/zips stored uncompressed) and written in ~1 MB pieces (native append), and a failed backup removes its partial file. Restore is still whole-file.
22. **Queue vs steer.** Typing while a reply runs queues the message (sent after the reply; Stop pauses the queue). Steer injects it at the next agent step (stored on that round, so history stays correctly ordered), or interrupts a plain reply because it has no steps. Queued messages auto-send only while you are in that chat.
23. **Browser handoff.** The assistant can put its hidden WebView on screen with a native Done/Cancel bar so you can sign in or solve a captcha yourself; passwords never pass through the assistant. Cookies persist and are shared with the in-app site browsers (a known trade-off).
24. **Errors reach the agent.** A tool that throws now comes back to the model as a failed result (it was escaping the tool loop and silently ending the reply), and if the previous reply stopped with an error, the next request carries a short system note about it so "try again" / "what went wrong?" has context. Browser: the page is still closed after every reply, but the last page reopens automatically (cookies keep sign-ins; element numbers are new, so click/type are not blindly replayed). `read` takes `offset`/`max_chars` for long pages, `scroll` follows the page's inner scroll container, and `key` sends PageDown/PageUp/Home/End or other keys.
25. **Watching the browser is view-only.** A monitor button in the chat header (only while a page is open) puts the agent's WebView on screen with a Close bar; the agent keeps running. A handoff replaces the watch view. Cost: the page lays out at screen size while watched.
26. **The browser stays open between replies.** It was closed at the end of every reply, which broke any task longer than a few tool rounds (the agent's step limit ends a reply). Now it closes after 10 idle minutes (or on `close`); a reopen returns to the last page and scroll position. `read` has `full:true` to scroll through and merge virtualised documents (Notion), `scroll` takes `y`/`amount`, `open` retries once on a network error, and typing into an editable page block needs `force:true`. `eval` runs a script in the page (like Playwright's `page.evaluate`, async ok, result capped at 20k chars) so the agent can pull structured data from wikis/tables; the owner judged it safe because the app is sandboxed on Android. It runs only in the opened page's own origin, with the same private-network blocks.
27. **The message field itself becomes the code box.** While the caret is inside a ``` block the field turns monospace/dark with a small bar (language, Wrap, Done to step out). No separate preview above it.
28. *[Server-sent downloads work since 113.]* **Browser tool follows Playwright's page API as far as a phone WebView allows.** Locators (css, `text=`, `role=…[name]`, `label=`, `placeholder=`, `testid=`, `alt=`, `title=`, xpath, `nth`), click/dblclick/right_click/hover/focus/check/uncheck/type/select/press (modifiers)/keyboard_type/mouse/drag, wait_for, get, query_all, content, eval, console, network, dialog (auto-accepted, recorded), block (fetch/XHR), storage, cookies (script-visible only), reload/forward/back, viewport. The in-page half lives in `src/pagescript.js` and is tested in real Chromium (`tests/e2e/pagescript.spec.js`). **Added since:** `upload` (decision 76: workspace files into a file field or a drop zone – the page gets a File built from the workspace bytes, and it posts as normal multipart; there is no OS picker unless the user has the page on screen in a handoff) and `pdf`. **Not possible / not done:** several tabs (window.open and target=_blank stay in the one view), saving a file the page downloads through the server (it is reported with its address; a download the page makes itself IS saved to the workspace), tracing/video/codegen, HttpOnly cookie access, response mocking, other browser engines, trusted (isTrusted) input events — everything is synthesized in-page, so a few strict sites may ignore it.
29. **MCP tool lists are remembered.** The "connecting to MCP servers…" card only shows the first time a server is used. After that the saved tool list (kept across app restarts) is used at once and refreshed in the background when over 10 minutes old; a server that failed is not retried for 2 minutes; the tools/list timeout is 15 s (tool calls keep 45 s). Settings → refresh still forces a fresh connect.
30. **One browser per chat.** Each chat has its own WebView, page, idle timer and last-page memory (native sessions keyed by chat id; `main` is used by preview_page). Sign-in cookies are still shared by Android, so a login in one chat works in the others. The monitor button follows the chat you are looking at. Memory cost: each open page holds a WebView until its 10-minute idle close.
31. **Reading a whole virtualised document merges by block id, not by text.** `read full` scrolls screen by screen, waits for each screen to settle, takes each block's OWN text (nested blocks are not copied into their parents), and merges by Notion block id so repeated headings in the source stay while the overlap between screens goes; pages without block ids merge by exact text overlap. A jump with no overlap is retried and then reported: the header says "Whole document read" only if the end was reached with no gap, otherwise "PARTIAL read" with the scroll positions. Also: eval may run 45 s, `steps` runs up to 30 actions in one call, and max_chars below 500 is honoured.
32. **Built-in Linux via proot.** Android (targetSdk ≥ 29) will not run programs downloaded into app storage, so proot is shipped as native libraries (`libproot.so`, its loader, libtalloc, libandroid-shmem — fetched from the Termux package repo by `scripts/fetch-proot.sh` in CI and patched with patchelf so the linker finds them by file name; packaging uses `useLegacyPackaging` so they exist on disk). The Alpine mini root filesystem (~4 MB, SHA-256 checked against Alpine's index) is downloaded on demand into `files/linux/rootfs` and unpacked with the system `tar`. One persistent `sh` per chat (end-of-command marker protocol, no PTY: full-screen programs like vim/htop do not work). The `shell` tool is off by default (Settings), the terminal sheet is Settings → Linux terminal. arm64 only. Since decision 33 the shell sees the chat's workspace at `/workspace` and the linked phone folder at `/phone`; it cannot see anything else of the app's data, and it has network access. Known unknowns until tried on a phone: proot's ptrace/seccomp behaviour on the newest Android versions (`PROOT_NO_SECCOMP=1` is set), and speed (proot is slower than native).
33. **`/workspace` is a mount, and the copies around it are reconciled, not overwritten.** The shell gets a real bind (`-b <files>/shell/work/<chat>:/workspace`), one directory per chat; the app's in-memory workspace is reconciled against it by identity, so a file deleted on either side is deleted on the other. The first version copied "what was new" through the shell's stdin as base64: it had no shell→app direction at all (a file written in the shell was invisible to `read_file`), deletes propagated nowhere — which left AES keys and cookie jars a tool had deleted sitting root-owned in the shell — an 8 MiB per-file ceiling, a 1.6 MB/s pipe, and an oversized file was re-read on every later command. All five came from it being a copy; the mount and `src/mirror.js` remove four of them and make the fifth (a refusal) remembered instead of retried. The linked phone folder is `/phone`: a proot bind when Android exposes a plain path (`FolderPlugin.localPath`), otherwise a mirror reconciled the same way, with writes back following Review/Auto/Read-only. Deletes are only propagated *from* the shell for the workspace; a file removed in the shell is never deleted from the phone folder, because that is the direction where a mistake loses the user's data.
34. **Long commands get a handle, helpers get one home, every result carries evidence.** Three failures cost this app's owner more time than any feature: 15 of 35 shell calls were `sleep 40; cat log`; the visible copy of a helper script drifted from the real one; and a check reported "ok" without exercising the path. So: (a) a command that outlives 30 s returns `{job_id, partial_output}` and `shell_job` polls/waits/kills it; the native timeout no longer kills the shell (it drains the timed-out command's output up to its own marker instead), and inside the shell the same thing is spelled `job run`/`job out`; (b) `src/toolkit/` is the only copy of `job`, `doctor` and `toolkit-pull` — installed into `/usr/local/bin` and re-verified by hash on every shell start, a drifted copy is overwritten rather than trusted; (c) every tool result ends with `[surface=… ok=… bytes=… ms=… proof=…]`, and tools that claim success supply real evidence (exit code, hash of the file written, HTTP status, a read-back after writing to the phone folder). `doctor` exercises each surface before a task instead of reading a flag, and `reload_tools` re-reads the MCP registry so an enable button takes effect without a new chat. Cost: ~80 characters per tool result, a few extra milliseconds per shell call for the index, and a 30 s wait on the first long command before a handle appears.
35. **A failed transfer must never become an edit.** The first version synced a 64 MiB file by handing the whole thing to the bridge as base64; the heap ran out, Capacitor left a zero-byte file at the destination, and the pass that prefers the shell side wrote that emptiness over the good copy - silent data loss, reported as a successful sync. Now a write goes to `<path>.ocm-tmp` in 4 MiB chunks, the byte count is checked, and only then is it renamed over the real name (a stale temporary is dropped on the next listing); the reconciler treats an empty copy as a failed transfer and puts the content back, distrusts a file that changed between listing and reading, removes and throws on a write whose size does not match, and reports a conflict instead of guessing when neither side has an agreement. The crossing cap is 32 MiB per file / 128 MiB per command because that is what the wasm heap can carry - bigger is refused cleanly and stays in the shell. Measured on the phone afterwards: 16 MiB at 20.9 MB/s (the pipe managed 1.6 MB/s), and the over-cap case leaves the app's copy intact. Mode is still not carried across a crossing; the toolkit verifier now checks the exec bit so a hash-correct but unrunnable script cannot pass.
36. **The sync carries metadata, not just bytes.** Every failure that cost a session was metadata: a mode bit, a directory, an emptiness, an exit code. So the reconciler now carries the exec bit with the file (`FileModePlugin` = the one thing Capacitor's Filesystem cannot see; the disk side reports it on the way in, the memory side remembers it, and the disk side re-applies `755` on the way out, so a script the app rewrites still runs), and deleting a file prunes the directories it was the last file in, on both sides (`FS.rmdir` in the Pyodide worker, a non-empty check + `rmdir` in `shellfs`). App-created files still arrive `600` - a mode only travels from the shell, because the app has no mode to give. A duplicate line in the sync note is deduped: a log that repeats is a log nobody reads.

37. **The app checks its own native half - both halves.** `adb shell am start -n dev.chronicle.app/.MainActivity --es selftest 1` + `adb logcat -s ChronicleSelfTest` runs two suites in one launch. The native one (SelfTestPlugin) exercises proot: rootfs, toolkit, a file written from the app and read through `/workspace`, one written from the shell and read back, and the **inode** on both sides - the only proof that a bind is a bind. The web one (src/selftest.js, woken by a one-shot flag MainActivity leaves for the WebView) runs the real bridge: mount, app→shell, shell→app, delete in the app and see `No such file` in the shell, delete in the shell and watch it leave the workspace. That is the test set that found the one-way sync and the silent deletes, so it is the test set that has to keep passing. Why: the whole point of a self-test is that "it compiles" and "it works" look identical in a handoff otherwise — and this app's bugs (one-way sync, silent deletes, an 8 MiB ceiling) all shipped green. Cost: one plugin, ~90 lines, and a build check that it is still registered.
38. **A stuck tool must never freeze a reply or block Stop.** Every tool call is raced against the Stop signal; `preview_page` (2 min) and `browser` (5 min) also have a time limit, after which the work is cleaned up (browser closed / shell killed) and the assistant gets an error result. Page previews time out per native step (draw 30 s, errors 10 s, screenshot 30 s) and free their WebView afterwards.
39. **Concurrency hygiene (audit).** Browser actions in one chat run one at a time (a per-chat queue), so two helpers or a steer cannot interleave on one page. The native shell keeps its sessions in a thread-safe map and caps the output a running command can pile up (newest 2 M chars kept); the tool abort race removes its listener when the tool finishes. Known and accepted: every open browser page holds a WebView until its 10-minute idle close; the terminal sheet keeps one output listener for the life of the app.
40. **GitHub Actions minutes are limited (2,000/month, 90% used on 10 Nov).** Tests run once per push (the pull_request run; pushes to main also), docs-only changes run nothing, and the APK is built on main, by hand, or when a branch commit message contains `[apk]`. Batch pushes: each one costs about 6 minutes of tests plus 3 for an APK.
41. **No dynamic import() of our own modules in the tool path.** `preview_page` used `await import("./browsercontrol.js")` (already imported statically elsewhere) and on the phone that never resolved: the card sat at "starting" for 100 s. It is a plain static import now. The stage display added in decision 33/40 is what exposed it.
42. **Vision is a per-model override, not only the provider list.** `supportsImages` obeys `settings.visionOverride[modelId]` first; the model sheet has a 👁 tap on every row to correct the list when it is wrong or silent (e.g. a new DeepSeek release). With vision on, tools like preview_page and browser screenshots hand the images straight to the model instead of going through a helper vision model.
43. **Pages the assistant writes load as data: URLs, which have no host.** The WebView request filter treated "no host" as a private address and answered 403 (ERR_HTTP_RESPONSE_CODE_FAILURE), so every preview_page screenshot was a "Webpage not available" error page. data: and about: requests now pass; http(s) to private/LAN hosts is still blocked.
44. **Hooks run in the chat's Linux, with Claude Code's exit-code contract.** `pre_tool` / `post_tool` (filtered by a tool-name regex), `stop` and `prompt`. Exit 2 blocks (refuses the call, sends the agent back to work, or stops the message); any other non-zero exit is only reported. The command gets `TOOL_NAME`, `TOOL_ARGS`, `TOOL_RESULT`, `CHRONICLE_EVENT` and starts in `/workspace`. They go through the same `shell` runner as the agent (mounts, jobs), a slow one is waited for up to its own timeout, and the stop hook runs at most 3 times per reply. Hooks only apply when tools are on. No hooks run without the built-in Linux.
45. **apply_patch accepts the Codex format and unified diffs; hunks are matched by content, not line numbers.** Trailing whitespace may differ, and hunks out of order are searched from the top. It is all-or-nothing, and a failed hunk returns the lines it expected so the model can rebuild the hunk instead of guessing. `repo_map` is regex-based (no parser), so it is cheap and works for many languages, but it can miss unusual definitions.
46. **Read-only calls in one round run in parallel, in order-preserving batches.** Contiguous read-only calls run together. A write splits the round, so reads after it see its result. This is off while tool hooks exist, because they share the chat's shell. (The first version ran all read batches before the writes; an e2e test caught the reads seeing stale text.)
47. **Roleplay gains SillyTavern's timed lorebook effects, chat variables and regex scripts.**
    - Sticky, cooldown and delay are counted in messages and stored per chat. They advance only when a reply really finishes, never for a preview or the inspector.
    - `{{setvar}}`, `{{getvar}}`, `{{addvar}}`, `{{incvar}}` and `{{decvar}}` (plus global variants) live in `conv.vars` and `settings.globalVars`. Like in SillyTavern, a macro that changes a value runs every time its text is used in a prompt.
    - Regex scripts have three stages. "Saved" rewrites the stored message once. "Only shown" changes the rendering. "Only sent" changes the request.
48. **Scene tracker (like RPG Companion / zTracker, kept small).** It is a "Field: value" sheet that a fast model updates after each roleplay reply, using the newest messages only. It is sent with every message and also written into chat variables. It costs one small request per reply, so it is off by default (Settings › Roleplay) and can be set per chat in the chat sheet. Stat-heavy trackers were left out: users report they bloat context and worsen prose.
49. **Opening a long chat follows the end for a few frames.** Messages off screen are laid out with a guessed height (`content-visibility`), so the ones that came into view grew and left the view about 5,000 px above the end. Not done on the start screen.
50. **Tool permissions: allow / ask / never per tool (like OpenCode), plus a default for every MCP tool and every mod tool.** "Ask" reuses the per-chat question sheet: Allow once, Allow for this chat (kept in `conv.allowedTools`), Deny, or a typed answer that is handed to the agent as the reason. A Stop while it waits counts as Deny. Nothing is asked by default, so existing chats behave as before.
51. **`/guide <text>` steers the next reply without a chat message (Guided Generations).** It is the same guidance path as "retry with guidance" (prompt `retry_guidance`): after a reply it continues the story, and after an unanswered message of yours it answers it. Story memory and the scene tracker are hidden from the chat sheet of ordinary chats unless they are switched on there.
52. **Build numbers are a clock, not a counter.** `versionCode` is minutes since 2026-01-01 UTC, in CI and in `scripts/build-local.sh` alike, and gradle uses the same clock when nothing is passed. The CI run number (195) and the local "+1 on whatever is installed" (229) were two separate counters, so CI builds looked older than local ones and were never offered (Android would also refuse them as a downgrade). Now the newer build always has the higher number, wherever it was built. The release says `Build #<that number>`, which the update check compares.
53. **Back in the Chub / BotBooru / Character Archive browser goes back a page.** Since the app targets Android 16, the system uses predictive back and no longer calls `onBackPressed()`: Back just closed the screen. The activity now registers an `OnBackInvokedCallback` (API 33+), which goes back a page and only leaves on the first page; `onBackPressed()` stays for older Android.
54. **Many extra tools are deferred, like Claude Code's tool search.** Saved tools, MCP tools and mod tools are sent with every request. Above 12 tools or 8,000 characters of definitions, only their names and one line each go out, inside the description of `load_tools`. The agent loads the ones it needs by name or search word, and they stay loaded for that chat (`conv.loadedTools`). A tool it has just saved is loaded at once. Helper agents get only the loaded ones. Built-in tools are always sent in full.
55. **Auto-compact threshold, as a default and per model (like Claude Code's).** It is either a share of the model's context (50–90 %) or a fixed number of tokens (32K–400K), capped at 95 % of the model. A fixed number also works for models whose limit is unknown. `/compact <focus>` compacts now and tells the summary what it must keep. Chats with a sliding window and roleplays still never compact.
56. **`@path` attaches a snapshot.** When you send, the file's text is stored with your message (20K characters per file, 6 files at most), so a retry or a later look sees what you actually sent. The model is told it is a snapshot. Persona `@mentions` work as before. The `@` menu lists files after personas, and a query containing `/` or `.` shows only files.
57. **The project folder: `.chronicle/` or `.claude/` in the workspace.** It holds `commands/*.md` (with `$ARGUMENTS`, `$1`…), `agents/*.md` (front matter: name, description, tools = none/read/full or a list of tool names, model) and `styles/*.md`. They are read from the chat's workspace on every request, so writing one takes effect at once. A project command beats a snippet of the same name, and the `.chronicle/` copy beats `.claude/`. A named agent's model is used when it is in the model list, otherwise the helper model.
58. **`# ` remembers instead of sending.** With tools on, the line goes under "## Notes" in AGENTS.md, which is sent with every message. Without tools it becomes a global memory. Only "# " with a space counts: `##` headings and `#hashtags` are sent normally.
59. **One mode chip: Auto, Ask first and Plan.** "Ask first" turns every write-type tool (planmode's `WRITE_TOOLS`) into "ask" for that chat, on top of 🔐 Permissions; "never" stays never. Plan toggles plan mode, which made the separate plan chip redundant, so it is hidden. The phone-folder mode is in the same sheet when a folder is linked.
60. **Reply styles are prompts, not system-prompt replacements.** Default, Concise, Explanatory and Learning, plus the project's own styles, are added to the system prompt. They are not used in roleplays.
61. **Rewind undoes the later replies' file checkpoints, newest first, and/or drops the later messages.** Your message returns to the box. Phone-folder changes are not undone by rewind, and the result says so; each reply's own ↩ Undo still does that. A checkpoint that was already pruned is reported, not hidden.
62. **Each persona has its own toolset, like a DeepSeek preset that only carries the tools it needs.** Persona editor › 🛠 Tools sets whether its chats start with tools on or off, and which groups it gets. The groups are web, Python and saved tools, files, shell, browser, previews, helpers, creator, phone folder, skills, autonomy (goals, schedules, scripts, old-chat search), MCP and mods. Presets: All, Coding, Research, Roleplay (web only) and None. Only switched-off groups are stored, so a new group is on by default. A persona without MCP does not even connect to the servers. The planning tools (to-do, ask) and doctor are always there because they are small. `persona.tools: false` now really means off (before, a false fell back to the app default).
63. **The creator tools assign tools too.** `save_persona` and `save_character` take `tools` (on or off at start) and `toolset` (the groups it gets, from the same list as the editor), and the approval sheet shows them. Left out, the app default applies for a new persona and the current setting stays for an update. The creator prompt asks the model to give each persona only what it needs.
64. **Changing a persona, character or lorebook is an edit, not a rewrite.** `edit_persona` changes a chat persona or a character in place:
    - `edits` are exact text replacements inside one field, like `edit_file`.
    - `set` replaces whole fields.
    - `add_greetings` / `remove_greetings` change the extra greetings.
    - `tools` / `toolset` change its tools.

    `edit_lorebook` adds, updates and removes entries. An entry is found by its name or one of its keys, and its content can take exact edits. The approval sheet lists exactly what changes. Before this, the only route was `save_persona` or `save_character` with `replace`, which re-sent everything. That made the model rebuild the character from scratch and drop details. The full-save tools stay for real rewrites.
65. **The workspace tools can move and delete.** `move_file` renames, moves or copies files and folders (binary too); `delete_file` removes a file or a folder. `delete_file` had a handler but was never offered to the model, so deleting needed the shell or Python.
66. **Skills can be edited, not only saved.** `edit_skill` changes a saved skill in place: exact edits in its instructions or a reference file, adding, replacing or removing files, a new description or name, on or off, or delete. It is offered once at least one skill exists. `save_skill` still creates a skill, or rewrites one completely.
67. **The agent can look after what was saved, not only add to it.**
    - `memory` lists, adds, edits and forgets the user's memories: shared by everyone, or this persona only. It refuses duplicates.
    - `saved_tools` lists, reads, switches off and deletes Python tools made with `save_tool`.
    - `manage_mod` switches a mod on or off, or removes it after asking.
    - `read_lorebook` lists all lorebooks or reads one, including lorebooks not attached to a character.
    - `edit_persona` and `edit_lorebook` can delete, after asking. Built-in personas can't be deleted.
    - The approval button now says what happens ("Add it", "Change it", "Delete it") instead of always "Add it".
    - Plan mode treats only the changing actions as writes. Helper agents and scripts can't use the managing tools.
68. **You can answer from the notification.** A "reply ready" notification has a reply box; what you type is sent to that chat, or queued if the chat is busy or on screen. A question or tool permission asked while the app is in the background becomes a notification with up to three option buttons and an Answer box; answering it resolves the oldest open question in that chat, and answering in the app clears the notification. Answers given while the app was killed are queued natively and read at the next start.
69. *[The background scheduler came with 78.]* **A reply that failed on an OpenCode Go limit tries again by itself.** The usage endpoint gives each limited meter's reset time; the retry is planned for 30 s after the latest of them (every limit must clear), shown under the error with Cancel, and checked every 30 s and when the app comes back. It only fires while the last message is still that failed reply, and only while the app runs (a background scheduler comes later). On by default; Settings › Notifications.
70. **Rewrites are edits you approve.** "Correct it with an instruction" asks the reply's own model to change only what you say, shows a word diff, and Keep replaces the reply (as an edit of the same version). `/polish` tidies your draft with the helper model and puts it back in the box; `/unpolish` restores your words. The draft in the box is saved as you type and when the app goes to the background, and comes back at the next start (for a week).
71. **The quick-reply bar is snippets.** A snippet can be shown as a button above the box everywhere, in chats or in roleplay; tapping it fills the box (with what you typed as `{{text}}`) or sends at once if the snippet sends right away. "Continue" starts on the roleplay bar.
72. **Choice chips are part of the reply, hidden.** With "Offer choices" on, roleplay replies end in a `<choices>` block. The block is hidden while streaming and after, is never sent back to the model, is not read aloud, and its 2–4 options appear as buttons under the newest reply only.
73. **`{{if}}` is resolved before the other macros.** Innermost first, so they nest; the branch not taken is removed before anything in it runs, so a `{{setvar}}` there does nothing. Conditions: a macro having a value, `var::`/`globalvar::` compared with `== != < > <= >=` (numbers as numbers, text ignoring case), and `!`.
74. **Tokens are put down to where they went.** Every request is recorded under a source: a reply, a tool (the step after a tool's result is put down to that tool, the first one when a round had several), an MCP server, or a helper job (titles, memory, compaction, story memory, corrections…). The usage sheet shows the last 30 days by source.
75. **Old memories carry their age.** A memory not updated for a month is sent as "(noted 3 months ago)", and the memory header says such notes may be out of date. Pinned ones are sent without an age. One not confirmed for half a year shows "is this still true?" in the memory list; "Still true" refreshes it.
76. **Files go into a page by script, like Playwright's setInputFiles.** `browser` action `upload` builds the files from the workspace into the page's file field (or drops them on a drop zone); 15 MB at most. A page that opens its picker while the agent drives is told no, and the agent is told to use upload. While the user has the page on screen (handoff), the picker opens the phone's file picker.
77. **`android_intent` is a closed list of hand-offs.** Open a web page, dial (the dialer only), text and email drafts, map, calendar event, alarm, timer, share, a settings page, or launch an app. Each one opens the other app for the user to finish; nothing is sent or saved by itself. The user is asked before every one. The native side checks the action and the address again (VIEW only for http(s) and geo, INSERT only for calendar events), so a mod can't widen it.
78. **Android wakes the app for its own work.** The app hands Android a wake plan: every scheduled task, usage-limit retry and proactive message time, the next 40, sent again only when it changes and every time the app goes to the background. One AlarmManager alarm (allowed while idle; exact if the user allows "Alarms & reminders", otherwise it may come a few minutes late in Doze) fires for the earliest. A running app gets a `wake` event and does the work at once. If Android has closed the app, each due item becomes a notification that opens its chat, and the app does the work on opening; JavaScript can't run without the app. The plan is re-armed after a restart or an update. No WorkManager: AlarmManager is built in, and nothing here needs a network-constrained job.
79. **Proactive messages are opt-in twice and bounded.** Off unless Settings › Notifications › "Characters can message me first" is on and the chat allows it (chat sheet › Can write first: after 2 h … 3 days of quiet). Never in the quiet hours (default 22:00–08:00, moved to the morning), at most N a day across all chats (default 3), once per silence (only after a finished reply, and not again until you answer), never in group chats, and not after today's token budget is spent. The message is generated like `/guide` continuing the story, with an in-character "you write first" instruction, marked "💬 Wrote first", and announced by the usual notification with its reply box.
80. **Voice mode listens inside the app, so it needs the microphone.** Hold the mic button (or `/voice`) for a hands-free loop: listen with live text on screen, send, read the reply aloud sentence by sentence while it is still being written (code blocks are skipped; *actions* and dialogue-only follow the read-aloud settings and the persona's voice), then listen again. Tapping the circle interrupts the reply and listens; while listening it sends what was heard. Two silences pause it; "stop" ends it. RECORD_AUDIO was stripped before because dictation uses the system's own listening screen; it is back, asked for only when voice mode starts. Without it, voice mode still works, but each turn opens Android's listening screen.
81. **MCP servers can be signed in to (OAuth 2.1 + PKCE, per the MCP authorization spec).** A 401 marks the server as needing sign-in, and Settings › MCP servers shows Sign in. Discovery: WWW-Authenticate's resource_metadata, else `/.well-known/oauth-protected-resource`, then the authorization server's metadata (RFC 8414, path-aware, OpenID as a fallback). The app registers itself by dynamic client registration (or uses a client id you give) and reuses that registration. The page opens in Custom Tabs and returns to `dev.chronicle.app://oauth/callback`; the state is checked, S256 is required, and `resource` is the server URL. Tokens are stored with the server like a hand-entered token and sent as Bearer. They are refreshed a minute before they run out, or once on a 401. Sign out forgets them.
82. **stdio MCP servers run in the app's Linux behind a bridge.** A command in the MCP "URL" box (`npx -y …`, `uvx …`, `python3 server.py`) becomes a stdio server. The shell has no stdin channel, so `mcp-bridge`, a stdlib-only Python script shipped and hash-checked with the toolkit, starts the server and serves it as Streamable HTTP on `127.0.0.1:<port>`. The port is stable per server (39100–39899), and every request needs that server's random secret, because other apps can reach localhost too. The ordinary MCP client then talks to it, so tool lists, caching and calls are shared with remote servers. The bridge is started on first use, after installing Python and the command's runtime (Node for npx, uv for uvx). It is started again, and the server re-initialised, when a request finds it gone, e.g. after Android closed the app. Requests the server makes to the client (sampling, roots) are answered "not supported".
83. **One on-device index serves search by meaning and roleplay recall.** It is built only when 🧠 Smart memory is on, because that is what downloads EmbeddingGemma. Every message of at least 24 characters (not hidden, not a greeting, choices removed, first 1000 characters) gets an int8 vector, stored per chat in IndexedDB (`vec:<chat id>`). The key is the message's time plus a hash of its text, so an edited message is embedded again and a deleted one drops out. The index fills 16 messages at a time every 30 s while nothing is running and the app is on screen; deleting a chat deletes its index.
    - **The drawer search** keeps its word matches and adds "≈ About this, in other words": chats whose best message is close in meaning (cosine ≥ 0.3).
    - **`search_chats`** merges both: chats found both ways first, then by meaning, then by words. Meaning-only hits are labelled.
    - **Recall** (Settings › Roleplay › Recall earlier moments, on by default but needing smart memory) applies once older messages have left the prompt (sliding window or compaction). After each reply, the earlier messages that best fit the last three are worked out (cosine ≥ 0.35, at most 3), and the next request carries them, in story order, as "[Recalled from earlier in this story …]". Working it out after the reply means sending never waits for the model.
84. **Recipes are Markdown workflows that the chat runs step by step.**
    - **Format:** front matter gives `name`, `description`, `params` (`topic (required), days = 7`) and an optional `schedule` (`daily 08:00` or `every 90`, in minutes). Each `## heading` is a step. `## Use: other-recipe key=value` runs another recipe, at most 3 deep and with no loops. `{{param}}` is filled in; other `{{…}}` are left for the chat's macros.
    - **Running:** `/name` with parameters (named, or plain words in order) checks every required parameter first. Then each step is sent as a message, tagged "🧪 name 2/3 · title", once the reply before has finished. An error or Stop ends the recipe.
    - **Where recipes live:** your own are in Settings › Recipes. A project's are in `.chronicle/recipes/`, and a project recipe wins over one of yours with the same name.
    - **Scheduling:** "Schedule" puts the recipe on the chat's schedule using its own schedule line, through the same wake plan as scheduled tasks.
    - **Import from a link:** GitHub blob and gist links are turned into raw ones. The recipe always opens in the editor first, with every hidden character (zero-width, bidi controls, Unicode tags, variation selectors) shown as ⟦U+XXXX⟧ and a warning. Saving removes them.
85. **Git history without Linux (isomorphic-git).** A chat's workspace can have a real git repository; turn it on in Chat files › 🌿 Git history.
    - **Where its data lives:** beside the workspace (IndexedDB `git:<chat>`), not as `.git` files in it, so the tools, the file list and the Linux copy don't see it. The filesystem adapter gives files a hash as their inode, because a workspace edit can keep the size and time.
    - **Commits:** with history on, every reply whose checkpoint changed files becomes a commit, named after your request.
    - **Restore:** puts the files back as they were at an earlier commit and records that as a new commit, so nothing is lost.
    - **Clone:** fills an empty workspace (depth 50, one branch) and turns history on.
    - **Pull:** fast-forward only; when both sides have new commits it says so and does nothing.
    - **Push:** uses the GitHub token from Settings › Updates.
    - **Network:** on Android git goes through a new native binary request (`GoStream.fetchBytes`, buffered, 100 MB cap); the existing streaming client is text only. In the web build, git hosts' missing CORS headers block clone, pull and push.
    - **Tested:** clone through the adapter against a public GitHub repo. Push was not tested with a real token.
86. **A pack is one JSON file that installs and removes as a unit.** `chronicle_pack: 1`, an id, a name and a version, plus any of `snippets`, `recipes`, `skills`, `mcpServers` and `personas`.
    - **Before installing:** you see every item, the count of hidden characters (removed on install), and every command its MCP servers would run.
    - **Installing:** every item is tagged with the pack id. Something of yours with the same name is kept and the pack's copy skipped. MCP servers from a pack are added switched off. A newer version replaces the old one's items.
    - **Removing:** Remove takes away exactly what the pack installed.
    - **Making a pack:** "Make a pack" exports your own snippets, recipes, skills and MCP servers. It never includes tokens or headers, and strips `VAR=value` prefixes from commands.
    - **Skipped:** mods are not in packs. They have their own permission review, and mixing the two would blur what you approved.
87. **The MCP registry browser shows what it would run before adding.** MCP servers › Find a server searches registry.modelcontextprotocol.io and keeps the latest version of each entry.
    - **Choosing an option:** a remote (Streamable HTTP) option is preferred, because nothing runs on the phone. Otherwise an npm or PyPI package becomes an `npx -y name@version` or `uvx name@version` command for the built-in Linux. The old SSE transport, docker and other package types are not offered.
    - **Adding:** the confirmation names the publisher (the registry namespace) and the exact URL or command, and says the registry does not vet servers. Required environment variables and secret headers are asked for, then the new server is tested.
88. **Other apps can run Chronicle, with a token each.** `chronicle://run?token=…&prompt=…` (or `recipe=name&args=…`, plus `persona=` and `id=`) opens a new chat named after the caller, runs it, and broadcasts `dev.chronicle.app.RESULT` with `text`, `ok`, `error`, `request_id` and `chat_id`. Tokens are made per app in Settings › Agent › 🤖 Automation and can be revoked; a link without a valid token runs nothing and says so. The reply broadcast goes only to the caller's package when it is known (Tasker, MacroDroid) or given (`reply_package`). Otherwise any app listening for that action could read it, which the help text says. A link is used rather than an exported broadcast receiver, because JavaScript must run and only the activity can start it, and Tasker's Send Intent and Browse URL both open links.
89. *[`script` is not in busybox: it comes from util-linux-misc, installed on first open – 116.]* **The full terminal gets a real PTY from busybox `script`, not from native code.** A PTY normally needs JNI (openpty), and there is no NDK in this build. Instead the shell plugin starts proot with `script -q -c "<program>" /dev/null`: `script` opens the pseudo-terminal inside Alpine and the app talks to it over plain pipes. The terminal's tty is written to `/tmp/ocm-pty-<id>`, so a new window size is `stty -F` on it plus SIGWINCH to every process reading from it. The screen is xterm.js (TERM=xterm-256color). Above the keyboard is a row with Esc, Tab, Ctrl, Alt, the arrows and `- / | :`; Ctrl and Alt apply to the next key. Checked: the same pipe-to-PTY approach with util-linux `script` on Linux (size, TERM, echo). **Not checked: busybox `script` under proot on a phone.** That is the first device test.

91. **PC agents over ACP, through a small bridge on the PC.** ACP is JSON-RPC over the agent's stdio, so `scripts/acp-bridge.py` (stdlib Python) starts the agent on the PC and serves it as POST /send plus long-polled GET /events?since=N, with a random secret on every request. It prints the address and secret to enter in Settings › Agent › 🖥 PC agents.
    - **The chat:** "New chat" makes a chat whose messages go to `session/prompt`. `agent_message_chunk` streams into the reply, `tool_call` and its updates show as lines with their status, a `plan` shows as the reply's note, and Stop sends `session/cancel`. `session/request_permission` uses the app's approval sheet, and also its notification when the app is in the background.

The new pages are ⚡ Shortcuts & recipes (snippets, recipes, packs), 🎛 Roleplay prompts & preset (main and post-history prompts, samplers, prompt note, prefill, impersonation, names, regex), 🔌 Connections (MCP servers, Linux terminal, OpenCode on PC, PC agents, automation), 🔊 Voice and 🔔 Notifications & background. For a big card picture that can take seconds on a phone (or never finish), and the previous chat's background stayed up meanwhile. Now the chat's own picture goes up at once and the screen-sized copy replaces it when ready, decoding gives up after 4 s, and the background is applied first in `updateHeader`, so nothing before it can stop it.   - *Stream → callbacks.* text_delta → onContent, thinking_delta → onReasoning (blocks separated), input_json_delta → onToolCallDelta, then `finalMessage()`: tool calls whose block closed (a call cut by max_tokens is not run), stop reason mapped (end_turn → stop, max_tokens → length so the "cut off" note shows, tool_use → tool_calls), usage converted so prompt tokens include cache reads and writes and `cached_tokens` = `cache_read_input_tokens` (the reply's "N% cached" and the usage view's per-model "(N cached)").
  - *Preserved thinking.* A reply's thinking / redacted_thinking blocks (with signatures) and the order of its text / tool_use blocks are kept on the round (`round.anthropic`) and on the finished reply (`msg.anthropic`) and sent back unchanged in later requests – only while the turn still says what it said (same text, same call ids); an edited reply goes without them. Other providers never get the field. Chronicle edits its history (older tool results trimmed, stale results stubbed, a sliding window, a rebuilt system prompt), which invalidates later blocks under Anthropic's conversation check (a 400 for accounts created from 2026-08-31). So a request that carries thinking blocks goes through `client.beta.messages.stream` with `thinking.block_binding.prefix_mismatch_behavior: 'drop_block'` (beta `thinking-binding-controls-2026-08-01`): an invalidated block is dropped by the API, the request proceeds. If such a request still fails with a 400 about thinking/signatures before any output, it is sent once more with every thinking block removed.
  - *Refusals and errors.* `stop_reason: 'refusal'` → the reply's error line: "Claude declined to answer this (category). explanation. You can rephrase it, or use ⋯ › 🔁 Retry with another model." Typed SDK errors: AuthenticationError → "Anthropic did not accept the API key… platform.claude.com › API keys", PermissionDenied, NotFound (model name), RateLimitError (HTTP 429, not retried), OverloadedError (529 → Chronicle's transient retry), APIConnectionError ("Network error – could not reach Anthropic"), other APIError "HTTP n – type: message" (so a "prompt is too long: N tokens > M maximum" still teaches the context limit).
  - *Not done / unverified:* no real API call was made (no key in the build environment) – the mock speaks Anthropic's SSE format and the unit tests answer the SDK at the fetch level; the server-side refusal fallback (`fallbacks`, beta) is not sent – a refusal says so and offers Retry with another model; `eager_input_streaming` is off (the API keeps validating tool input; a big write_file's arguments arrive in bursts); no prices for Claude models in the spend view (models.list has none); a roleplay prefill is dropped, not turned into an instruction.
  - *Refusal fallback on by default (added at merge):* for the models that take it (Opus 5.5, Opus 5, Sonnet 5.5, Fable 5.x) every request carries `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`), so a policy refusal is re-run by the API on a model it picks, in the same call, instead of ending in "Claude declined".   - The BSSID when Android shows it (precise location). Otherwise the gateway, the subnet and the DNS servers.
  - These come from a new permission-free `Phone.lanNet`.
  - On another network the addresses are blocked again, and `status` says so.
- **Where it is enforced:**
  - fetch_url reads an allowed address directly and never through the outside renderer or Exa, which must not be told it.
  - GoStreamPlugin's guarded reads (text, and the PDF bytes of decision 270) accept an allowed literal only for a request that starts there. A public page that redirects to the user's network is still refused at every hop.
  - The browser opens an allowed address with its list, and goes from there to another allowed one.
  - The browser never follows a redirect into the list from elsewhere.
  - The browser loads a local address only while the page shown is itself on an allowed one, so a public page reached from there cannot embed or fetch it.
- **Who never gets it:** helpers (delegate), Claude Code's cross tools, and scheduled or proactive runs. They get no grant at all.
- **Seen and taken back:**
  - A 🏠 chip above the message box shows the grant. Its sheet ("Allowed in this chat") lists it together with the calendar / contacts / location OKs of decision 270 and the tools allowed "for this chat".
  - Each can be taken back on its own, or all at once.
  - A branch of the chat starts with none of them.
- **Not covered:** downloads from a local address are still refused.

273. **The harness against injected content (field review: security engineer; built by a helper).**
- **run_python can no longer reach the app's data:**
  - Pyodide gets a short `jsglobals` list and a fetch that only downloads packages, by GET or HEAD with no credentials, from its own index or PyPI.
  - Once loaded, the worker loses IndexedDB, caches, XHR, WebSocket, EventSource, workers, importScripts and storage. If that cannot be done, Python does not start.
  - A short jsglobals alone was not enough: the Function constructor reaches the worker's global anyway.
  - Still possible: such code can `import()` a remote script, but there is no storage left to carry away.
- **Mods and run_script frames talk over a MessagePort**, handed to the frame's own page before its code runs.
  - A page the frame navigates to can neither send nor receive. A sandboxed frame keeps origin "null" after navigating, so an origin check would not have helped.
  - Navigation is cancelled where the Navigation API exists. A frame that leaves anyway says so on pagehide, and the mod stops.
- **A mod's `net:` permission holds on every hop:**
  - Redirects are followed by hand. Each hop must be https, inside the permission, and public by text and by resolved address (new `GoStream.checkPublic`).
  - Credentials are dropped when the origin changes.
- **browser `state save`** (cookies, sign-ins) asks every time and names the site. It is refused when nobody can be asked.
- **Browser LAN grant:** it is cleared once the main frame goes to a host outside it. A public page reached from a granted device can no longer post back to it (decision 271 covered HTTP 3xx only).
- **Console messages are caught natively** (onConsoleMessage) from the first line of loading. They are merged with the page script's log, so a startup error is no longer missing.
- **Credentials on redirects:** a guarded redirect to another origin sends only neutral headers (no Authorization, Cookie or API-key header).
- **Reads with your own headers never fall back:** with caller headers, or format raw / html, fetch_url never falls back to the outside renderer or Exa. It returns the origin's own status and body.
- **MCP secrets:** an MCP server's `headers` go to the secure store like its token. Backups leave out `headers` and `bridgeSecret`; a test checks that a backup zip holds no configured secret string.

274. **PC tools and the shell guard (field reviews: sysadmin, web developer, security; built by a helper).**
- **pc_shell asks before destructive admin commands:**
  - The line is split with the shell guard's lexer, unwrapping sudo, env, time, nohup and `sh -c`. It also reads what `ssh host "…"`, `powershell -Command`, `cmd /c` and `wsl` would run.
